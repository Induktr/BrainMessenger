# Руководство по Развертыванию BrainMessenger (Доставка Системы Пользователям)

### 1. Общая Информация: Реализация Актива в Рабочей Среде

**Название проекта:** BrainMessenger

**Описание:** Этот документ описывает **систематический процесс** (Принцип 9) перевода BrainMessenger из среды разработки в рабочую среду (продакшен), где он становится доступным пользователям и функционирует как **ценный цифровой АКТИВ** (Принцип 10). Развертывание включает настройку необходимой инфраструктуры, подготовку приложения и его запуск с учетом требований к **надежности и масштабируемости** (Принцип 3, 8).

**Цель:** Обеспечить **эффективный, автоматизированный и надежный** процесс развертывания BrainMessenger на выбранной облачной инфраструктуре, позволяющий приложению стабильно работать под нагрузкой и легко масштабироваться.

**Предполагаемая среда:** **Облачная инфраструктура** (например, Google Cloud Platform (GCP), Cloudflare, DigitalOcean, AWS) с поддержкой Kubernetes и управляемых баз данных.

**Принципы, которыми руководствуется развертывание:**

*   **Система и Оптимизация (Принцип 9):** Процесс деплоя построен как автоматизированный пайплайн (CI/CD), минимизирующий ручные ошибки и ускоряющий доставку. Инфраструктура описывается как код.
*   **Долгосрочное Мышление (Принцип 8):** Выбор масштабируемых технологий (Kubernetes, Neon, Cloudflare R2) для поддержки будущего роста.
*   **Качество > Количество (Принцип 3):** Надежность процесса деплоя (автоматизированные тесты, версионирование) важнее скорости, которая может привести к сбоям.
*   **Прагматизм и Реализм (Принцип 12):** Использование готовых облачных сервисов там, где это эффективно.
*   **Ответственность и Проактивность (Принцип 6):** Каждый член команды отвечает за корректную настройку окружения и мониторинг после деплоя.

### 2. Требования к Инфраструктуре: Фундамент для Работы Системы

#### 2.1. Минимальные Ресурсы (для MVP, ~1000 активных пользователей)

*   **Виртуальные Машины/Ноды Kubernetes:** Минимум 2-3 ноды для отказоустойчивости.
    *   **Спецификации Нод:** 4 vCPU, 8-16 ГБ RAM каждая.
*   **База Данных (Neon/PostgreSQL):** Выделенный инстанс в Neon.
    *   **Спецификации:** Тарифный план с достаточным объемом хранилища (старт с бесплатного 30ГБ, готовность к переходу на платный ~$150/мес за 113ГБ).
*   **Хранилище Файлов (Cloudflare R2):** Активный бакет.
*   **Кэширование (Redis):** Выделенный инстанс или кластер. 4-8 ГБ RAM.
*   **Очередь Сообщений (Kafka):** Кластер (минимум 3 брокера для отказоустойчивости) или управляемый сервис.
*   **Публичный IP-адрес:** Для доступа к API Gateway/Backend.
*   **Доменное имя:** Например, `brainmessenger.com` с поддоменами (`api.brainmessenger.com`, `r2.brainmessenger.com`).
*   **SSL/TLS Сертификат:** Для безопасных соединений (TLS 1.2+).

#### 2.2. Зависимости на Сервере/CI

*   **Docker Engine:** 20.10+
*   **kubectl:** Последняя стабильная версия (для управления кластером Kubernetes).
*   **Terraform:** 1.5+ (для управления инфраструктурой как кодом).
*   **Git:** Для получения исходного кода.
*   **Учетные данные облачного провайдера:** Настроенные для Terraform и kubectl.
*   **Учетные данные внешних сервисов:** API ключи для Neon, Cloudflare R2, Firebase, Stripe, Gmail API.

### 3. Подготовка Инфраструктуры: Описание Системы как Кода (IaC)

Мы используем **Terraform** для описания и автоматического создания всей необходимой облачной инфраструктуры. Это часть нашей **системы автоматизации** (Принцип 9).

1.  **Клонирование репозитория:**
    ```bash
    git clone <URL вашего репозитория>
    cd BrainMessenger
    ```
2.  **Настройка провайдера Terraform:**
    *   В файле `infrastructure/main.tf` или в отдельном файле `provider.tf`, настройте провайдер для вашего облачного провайдера (GCP, AWS, Azure, DigitalOcean).
    *   Настройте аутентификацию для Terraform (например, через переменные окружения, файлы ключей или аутентификацию облачного провайдера).
3.  **Определение ресурсов в Terraform:**
    *   В файлах `.tf` в папке `infrastructure/`, опишите необходимые ресурсы:
        *   Кластер Kubernetes (GKE, EKS, AKS, DigitalOcean Kubernetes).
        *   Правила фаервола (открытие портов 80, 443, портов Redis, Kafka и т.д.).
        *   Настройки DNS (записи A/CNAME для домена и поддоменов).
        *   (Опционально) Выделенные ВМ, группы масштабирования.
4.  **Инициализация Terraform:**
    ```bash
    cd infrastructure
    terraform init
    ```
5.  **Просмотр плана выполнения:**
    ```bash
    terraform plan
    ```
    *   Внимательно проверьте план, чтобы убедиться, что Terraform будет создавать, изменять или удалять ожидаемые ресурсы.
6.  **Применение конфигурации:**
    ```bash
    terraform apply
    ```
    *   Подтвердите выполнение, введя `yes`.

*Результат:* Создана базовая инфраструктура в облаке, готовая к развертыванию приложения.

### 4. Подготовка Приложения: Сборка Контейнеров

Приложение контейнеризируется с использованием **Docker**, что обеспечивает переносимость и изоляцию.

1.  **Сборка Docker-образов:**
    *   Мы используем монорепозиторий и Turborepo. Dockerfile находятся в папках каждого пакета (`backend/Dockerfile`, `packages/web/Dockerfile`).
    *   Используйте многоступенчатую сборку для уменьшения размера финальных образов (см. DocDevIn.md, раздел 9.3).
    *   Выполните сборку образов, используя команды из Dockerfile:
        ```bash
        # Пример сборки backend образа
        docker build -t brainmessenger-backend:latest ./backend
        # Пример сборки web образа
        docker build -t brainmessenger-web:latest ./packages/web
        # Пример сборки Kafka Worker образа
        # docker build -t brainmessenger-image-worker:latest ./backend/workers/image-processing # Если воркеры отдельные
        ```
2.  **Версионирование образов:** Используйте Git Commit SHA или семантическое версионирование для тегов образов: `brainmessenger-backend:<commit_sha>`. Это важно для надежности и возможности отката.
3.  **Публикация образов:** Загрузите собранные образы в реестр контейнеров (Docker Hub, Google Container Registry, GitLab Registry и т.д.).
    ```bash
    docker tag brainmessenger-backend:latest your-registry/brainmessenger-backend:<commit_sha>
    docker push your-registry/brainmessenger-backend:<commit_sha>
    # Повторите для других образов
    ```

*Результат:* Готовые к развертыванию Docker-образы приложения находятся в реестре контейнеров.

### 5. Конфигурация Окружения: Настройка Системы через Переменные и Секреты

Конфигурация приложения осуществляется через **переменные окружения**. Чувствительные данные хранятся в **секретах** Kubernetes.

#### 5.1. Переменные Окружения

Переменные окружения задают настройки приложения (порты, URLs сервисов, уровни логирования) и учетные данные для интеграций.

*   **Общие переменные:** `NODE_ENV`, `PORT`, `APP_URL`, `LOG_LEVEL`.
*   **Переменные для интеграций:** `NEON_DATABASE_URL`, `R2_ACCESS_KEY`, `R2_SECRET_KEY`, `R2_ENDPOINT`, `R2_BUCKET`, `FIREBASE_API_KEY`, `FIREBASE_PROJECT_ID`, `REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD`, `KAFKA_BROKER`, `ENCRYPTION_KEY`, `STRIPE_SECRET_KEY`, Google API Keys и др.
*   **Настройка:** В продакшен-окружении (Kubernetes) переменные окружения должны быть заданы в манифестах деплоймента (`deployment.yaml`). **Чувствительные данные (ключи, пароли, секреты)** должны храниться не в открытом виде, а в **Kubernetes Secrets**.

#### 5.2. Kubernetes Secrets

*   Создайте Kubernetes Secrets из ваших чувствительных переменных окружения.
    ```bash
    kubectl create secret generic backend-secrets \
      --from-literal=JWT_SECRET='your-very-secure-secret-key-32-chars' \
      --from-literal=NEON_DATABASE_URL='postgresql://user:password@neon-host:port/dbname' \
      --from-literal=R2_ACCESS_KEY='your-access-key' \
      --from-literal=R2_SECRET_KEY='your-secret-key' \
      --from-literal=REDIS_PASSWORD='your-redis-password' \
      --from-literal=ENCRYPTION_KEY='your-32-byte-encryption-key' \
      # ... добавьте другие секреты
    ```
    *   **Важно:** Используйте надежные методы генерации ключей (`JWT_SECRET`, `ENCRYPTION_KEY`).
    *   Не коммитьте файлы, содержащие секреты, в Git. Управляйте их созданием безопасно (например, через зашифрованные файлы Terraform или CI/CD пайплайн).
*   В манифестах деплоймента ссылайтесь на эти секреты.
    ```yaml
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: backend
    spec:
      template:
        spec:
          containers:
            - name: backend
              image: your-registry/brainmessenger-backend:<commit_sha>
              env:
                - name: NODE_ENV
                  value: production
                - name: PORT
                  value: "3000"
                - name: JWT_SECRET
                  valueFrom:
                    secretKeyRef:
                      name: backend-secrets
                      key: JWT_SECRET
                - name: NEON_DATABASE_URL
                  valueFrom:
                    secretKeyRef:
                      name: backend-secrets
                      key: NEON_DATABASE_URL
                # ... добавьте другие переменные из секрета
    ```

#### 5.3. Настройка Базы Данных (Neon)

1.  **Создайте базу данных в Neon:** Если еще не сделали, создайте проект и базу данных в Neon.
2.  **Примените схему БД:** Используйте Prisma Migrate для развертывания схемы на созданном инстансе Neon.
    ```bash
    # Убедитесь, что NEON_DATABASE_URL задана в вашем окружении CI/CD или локально
    cd backend
    npm install # Установить зависимости для Prisma CLI
    npx prisma migrate deploy # Применить все непримененные миграции из папки prisma/migrations
    ```
    *   Эта команда должна выполняться как часть вашего CI/CD пайплайна перед деплоем нового образа Backend.
3.  **Настройте резервное копирование в Neon:** Используйте встроенные автоматические бэкапы в консоли Neon (на платных тарифах).

#### 5.4. Настройка Redis, Kafka и других зависимостей

Разверните Redis и Kafka (если используете) в вашем кластере Kubernetes или используйте управляемые облачные сервисы (например, Memorystore для Redis, Confluent Cloud или Kafka в K8s). Настройте их доступность для Backend-сервиса (например, через Kubernetes Services).

### 6. Шаги Развертывания: Автоматизированный Пайплайн

Процесс деплоя автоматизирован с помощью **CI/CD (GitHub Actions)** и **Kubernetes**.

1.  **Триггер:** Пуш кода в ветку `main` или `develop` (или создание Release Tag).
2.  **CI Pipeline (GitHub Actions):**
    *   Checkout кода.
    *   Установка зависимостей (с кэшированием Turborepo/npm).
    *   Линтинг и форматирование (проверка стандартов).
    *   Сборка проекта (Turborepo `turbo run build`).
    *   Прогон тестов (Unit, Integration, E2E) (Turborepo `turbo run test`). **Тесты должны пройти!**
    *   Сборка Docker-образов (`docker build`).
    *   Тегирование образов (`docker tag`) с использованием Git SHA или версии релиза.
    *   Публикация образов в реестр контейнеров (`docker push`).
    *   (Опционально) Сканирование образов на уязвимости.
3.  **CD Pipeline (GitHub Actions):**
    *   (После успешного CI в ветке, предназначенной для деплоя - например, `main`).
    *   Авторизация в облачном провайдере и кластере Kubernetes (`kubectl`).
    *   Обновление манифестов деплоймента Kubernetes (`deployment.yaml`) с новым тегом образа.
    *   Применение манифестов Kubernetes (`kubectl apply -f k8s/`). Kubernetes выполнит **Rolling Update** (плавное обновление подов).
    *   Проверка статуса деплоя (`kubectl rollout status deployment/backend`).
    *   (Опционально) Запуск пост-деплойментных тестов (например, Health Check эндпоинта).
    *   (Опционально) Уведомление о деплое (Slack, email).

#### 6.1. Продакшен-Развертывание (Kubernetes)

Манифесты Kubernetes (`k8s/`):

*   `deployment.yaml`: Описывает Deployment (какой Docker-образ использовать, сколько реплик, переменные окружения, секреты, Health Checks).
*   `service.yaml`: Описывает Service (как получить доступ к подам Deployment изнутри кластера).
*   `ingress.yaml`: Описывает Ingress (как получить доступ к Service извне кластера через публичный IP/домен, настройка SSL/TLS, маршрутизация запросов).
*   `hpa.yaml` (опционально): Horizontal Pod Autoscaler (настройка автоматического масштабирования подов по нагрузке - CPU/Memory).
*   `secret.yaml` (или создание через `kubectl create secret`): Определения Kubernetes Secrets.

**Шаги в CI/CD:**

```yaml
# Фрагмент .github/workflows/cd.yml
jobs:
  deploy-backend:
    runs-on: ubuntu-latest
    # Запускать только после успешного CI в ветке main
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4
      - name: Authenticate with Cloud Provider
        # Настройте аутентификацию (зависит от провайдера - gcloud auth, aws configure, etc.)
        # Используйте secrets GitHub Actions для учетных данных
        run: |
          echo ${{ secrets.GCP_SERVICE_ACCOUNT_KEY }} | base64 --decode > gcloud-key.json
          gcloud auth activate-service-account --key-file=gcloud-key.json
          gcloud container clusters get-credentials YOUR_CLUSTER_NAME --zone YOUR_CLUSTER_ZONE --project YOUR_GCP_PROJECT_ID
      - name: Update K8s Deployment with new image
        run: |
          # Получаем SHA текущего коммита или тег релиза
          IMAGE_TAG=${{ github.sha }} # Или ${{ github.ref_name }} для тега релиза
          # Обновляем манифест: находим образ для контейнера 'backend' и меняем его тег
          kubectl --namespace=default set image deployment/backend backend=your-registry/brainmessenger-backend:$IMAGE_TAG
      - name: Wait for deployment rollout
        run: kubectl --namespace=default rollout status deployment/backend --timeout=5m
      - name: Run post-deployment health check
        run: curl --fail https://api.brainmessenger.com/health
```

#### 6.2. Настройка Nginx/API Gateway (опционально, если не используется Ingress)

Если вы не используете Ingress контроллер Kubernetes или разворачиваете на ВМ, может потребоваться отдельный Nginx или API Gateway как обратный прокси, терминатор SSL/TLS и балансировщик нагрузки.

*   **Установка:** Установите Nginx.
*   **Конфигурация:** Настройте Nginx для проксирования трафика с публичного IP/домена на Backend-сервис (порт 3000). Настройте SSL/TLS сертификаты.
*   **Автоматизация:** Настройку Nginx также можно автоматизировать с помощью Terraform или Ansible.

### 7. Проверка Работоспособности: Убедиться, что Система Жива

После развертывания проведите проверки, чтобы убедиться, что приложение работает корректно.

1.  **Статус подов Kubernetes:** Убедитесь, что все поды в статусе `Running` и не перезапускаются.
    ```bash
    kubectl get pods
    ```
2.  **Статус деплоймента:** Убедитесь, что Rolling Update успешно завершен.
    ```bash
    kubectl rollout status deployment/backend
    ```
3.  **Логи приложения:** Проверьте логи Backend-сервиса на наличие ошибок при старте.
    ```bash
    kubectl logs <backend-pod-name>
    ```
4.  **Health Check Endpoint:** Выполните запрос к Health Check эндпоинту вашего API.
    ```bash
    curl --fail https://api.brainmessenger.com/health
    ```
    Ожидаемый ответ: `{"status": "ok"}` (или подобный).
5.  **Тест ключевого функционала:** Выполните простые действия в приложении (регистрация тестового пользователя, отправка сообщения). Проверьте логи и метрики.
6.  **Статус Базы Данных:** Проверьте доступность и базовые метрики БД через консоль Neon.
7.  **Статус других сервисов:** Проверьте доступность Redis, Kafka и внешних интеграций.

### 8. Масштабирование: Подготовка к Росту (Принцип 8)

*   **Горизонтальное Масштабирование (Kubernetes HPA):** Настройте Horizontal Pod Autoscaler (HPA) для автоматического увеличения/уменьшения количества подов Backend-сервиса на основе метрик (CPU, Memory, или кастомных метрик нагрузки API).
*   **Масштабирование Базы Данных:** Мониторьте нагрузку на Neon. Будьте готовы перейти на более высокий тарифный план или настроить репликацию/партиционирование (см. DocOptimizationIn) при росте нагрузки на БД.
*   **Масштабирование R2:** Cloudflare R2 масштабируется автоматически по объему данных.
*   **Масштабирование Redis/Kafka:** При росте нагрузки масштабируйте инстансы Redis/Kafka или переходите на управляемые кластеры.
*   **Переход на Микросервисы (долгосрочно):** Как описано в DocMigrationMicro.md, переход на микросервисную архитектуру позволит масштабировать отдельные компоненты приложения независимо.

### 9. Мониторинг После Деплоя: Постоянное Наблюдение за Системой

*   Настройте систему мониторинга (Prometheus + Grafana) и логирования (ELK/Sentry) для сбора метрик и логов с новых развернутых подов.
*   Настройте алерты для уведомления о проблемах (высокая задержка, ошибки, высокая нагрузка, перезапуски подов). См. DocMonLog.md.

### 10. Примечания

*   **CI/CD:** Инвестиции в надежный CI/CD пайплайн — это инвестиции в **эффективность** (Принцип 9) и **качество** (Принцип 3) процесса разработки и деплоя.
*   **Инфраструктура как Код:** Управление инфраструктурой через Terraform снижает риск ошибок конфигурации и упрощает воспроизведение окружений (dev, staging, prod).
*   **Безопасность:** Убедитесь, что все секреты надежно хранятся (Kubernetes Secrets) и не попадают в логи или Git (см. DocSecurity.md). Настройте фаерволы для ограничения доступа к сервисам только из необходимых источников.
*   **Откат:** Ваш CI/CD пайплайн должен позволять легко откатиться к предыдущей стабильной версии Docker-образов в случае проблем после деплоя (`kubectl rollout undo deployment/backend`).
*   **Документация:** Поддерживайте эту документацию в актуальном состоянии по мере изменения инфраструктуры или процесса деплоя.

Развертывание — это успешная реализация вашей **Системы Планирования** в действии, когда весь накопленный опыт и принципы воплощаются в работающем продукте для пользователей.
