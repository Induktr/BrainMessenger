# План Миграции на Микросервисы BrainMessenger (Стратегия Развития Актива)

### 1. Введение: Эволюция Архитектуры для Масштабирования

**Название проекта:** BrainMessenger

**Описание:** Этот документ описывает **стратегический план** (Принцип 4) перехода BrainMessenger от текущей монолитной архитектуры на NestJS к архитектуре, основанной на **микросервисах**. Этот переход является **долгосрочной инвестицией** (Принцип 8) и необходимым шагом в развитии нашего **цифрового АКТИВА** (Принцип 10) для достижения целей по масштабированию и добавлению нового функционала.

**Цель:** Обеспечить возможность поддерживать **1 миллион активных пользователей** (NFR-4) с сохранением и улучшением показателей производительности (<500 мс API, NFR-1), повысить **отказоустойчивость** (Принцип 3, 5), ускорить циклы разработки и деплоя, а также упростить интеграцию новых, специализированных функций (например, AI-ассистент, сложные боты).

**Текущий статус:** Монолитная архитектура (v1.0, март 2025), успешно построена и функционирует как **фундамент** (Принцип 8). Планирование и подготовка к миграции активно ведутся в Q4 2025 (см. Дорожную карту).

**Принципы, которыми руководствуется миграция на микросервисы:**

*   **Долгосрочное Мышление (Принцип 8):** Миграция — это инвестиция в будущее проекта, а не просто техническая перестройка.
*   **Система и Оптимизация (Принцип 9):** Переход к микросервисам — это трансформация всей системы, требующая переосмысления взаимодействия компонентов и процессов разработки/деплоя.
*   **Прагматизм и Реализм (Принцип 12):** Используется подход "Strangler Pattern" для минимизации рисков и постепенного перехода. Выбор сервисов для выделения основан на их связности и потенциальной нагрузке.
*   **Гибкость и Адаптивность (Принцип 11):** Микросервисы повышают гибкость архитектуры, позволяя легче добавлять новый функционал и адаптироваться к меняющимся требованиям.
*   **Качество > Количество (Принцип 3):** Каждый новый сервис должен быть высококачественным, надежным и иметь четкую ответственность.
*   **Настойчивость (Принцип 13):** Процесс миграции сложный и требует упорства.

### 2. Цели Миграции: Что Мы Получим от Новой Системы

*   **Улучшенная Масштабируемость (NFR-4, P8):** Возможность независимо масштабировать наиболее нагруженные или ресурсоемкие компоненты (например, сервис чатов, сервис звонков, сервис AI), не масштабируя весь монолит.
*   **Повышенная Производительность (NFR-1, P3):** Снижение зависимости между модулями, возможность оптимизировать стек и ресурсы под конкретную задачу сервиса, уменьшение "шума" между компонентами.
*   **Повышенная Отказоустойчивость (P3, P5):** Изоляция сбоев. Проблема в одном микросервисе (например, сервис AI временно недоступен) не приводит к полному отказу всей системы.
*   **Ускоренные Циклы Разработки и Деплоя (P9):** Команды (или отдельные разработчики) могут работать над разными сервисами и деплоить их независимо, уменьшая время вывода новых функций.
*   **Гибкость и Упрощение Разработки Новых Функций (P11):** Новые, специализированные функции (сложный AI-ассистент, платформа для ботов, интеграции) могут быть реализованы как отдельные микросервисы с оптимальным для них стеком, не утяжеляя существующий код.
*   **Технологическая Гибкость:** Возможность использовать разные технологии для разных сервисов, если это оправдано (хотя на старте предпочтительно придерживаться единого стека - NestJS).

### 3. Текущая Архитектура (Монолит): Наш Фундамент

*   **Описание:** Единое приложение на NestJS, содержащее большую часть бизнес-логики и предоставляющее GraphQL API.
*   **Технологии:** NestJS, PostgreSQL (Neon), Cloudflare R2, Redis, Firebase Admin SDK, Stripe SDK, Google APIs Client.
*   **Логическая Структура (Модули):**
    *   `AuthModule`: Регистрация, логин, JWT, 2FA, сброс пароля (Gmail API).
    *   `UserModule`: Управление профилями пользователей.
    *   `ChatModule`: Управление чатами и сообщениями, WebSocket Gateway.
    *   `CallModule`: Управление звонками и конференциями (WebRTC).
    *   `NotificationModule`: Отправка push-уведомлений (Firebase).
    *   `PaymentModule`: Управление Premium подпиской (Stripe).
    *   `FileModule`: Загрузка/управление файлами (Cloudflare R2).
    *   `KafkaModule`: Взаимодействие с Kafka для асинхронных задач.
    *   `GraphQLModule`: Настройка GraphQL API.
*   **Проблемы Монолита (Причины Миграции):**
    *   **Единая Точка Отказа:** Сбой в одном модуле (например, ошибка интеграции Payment) может потенциально затронуть все приложение.
    *   **Сложность Масштабирования:** Нельзя масштабировать только самый нагруженный модуль (например, Chat) без масштабирования всего приложения со всеми его зависимостями.
    *   **Зависимости между Модулями:** Сильная связанность между модулями усложняет их независимую разработку и тестирование.
    *   **Долгие Циклы Деплоя:** Даже небольшое изменение в одном модуле требует пересборки и перезапуска всего монолита.
    *   **Риски при Внедрении Новых Технологий:** Сложно интегрировать технологии, несовместимые с основным стеком NestJS, или требующие специфического окружения, без влияния на весь монолит.

### 4. Целевая Архитектура (Микросервисы): Наша Будущая Система

Архитектура микросервисов основана на принципе "один сервис — одна ответственность", четких границах и независимом взаимодействии.

*   **Основные Принципы Целевой Архитектуры:**
    *   **Single Responsibility Principle:** Каждый микросервис отвечает за ограниченный набор связанных бизнес-функций (Bounded Context).
    *   **Loose Coupling:** Сервисы взаимодействуют через четко определенные API (синхронно) или сообщения (асинхронно), минимизируя прямые зависимости.
    *   **Independent Deployment:** Каждый сервис может быть разработан, протестирован и деплоен независимо от других.
    *   **Resilience:** Сбои в одном сервисе изолируются и не влияют на работоспособность других сервисов.
    *   **Scalability:** Сервисы масштабируются независимо в зависимости от нагрузки на конкретный функционал.
*   **Предложенные Микросервисы (Первая итерация):**

  | Сервис         | Ответственность / Bounded Context | Ключевая Технология | Основное Хранилище | Связь с Принципами                                   |
  | :------------- | :-------------------------------- | :------------------ | :----------------- | :--------------------------------------------------- |
  | **API Gateway**| Маршрутизация, Агрегация API, Аутентификация (опционально) | Apollo Gateway / NestJS | Redis (для Rate Limit/кэша) | P9 (Система - единый вход), P3 (Качество - отказоустойчивость), P5 (Здоровье - защита от перегрузки). |
  | **Auth Service** | Аутентификация пользователей, JWT, 2FA, Сброс пароля | NestJS              | PostgreSQL (Neon)  | P5 (Здоровье - безопасность), P9 (Система - управление доступом). |

  | **Chat Service** | Управление чатами и сообщениями, WebSocket Gateway | NestJS              | PostgreSQL (Neon), Redis | P9 (Система - ядро общения), P3 (Качество - скорость доставки). |

### 5. Стратегия Миграции: Подход Strangler Pattern (Принцип 12)

Мы используем **Strangler Pattern** (Шаблон Дросселирования/Удушения) — **прагматичный** и менее рискованный подход, при котором новый функционал или выделяемые модули реализуются как микросервисы рядом с монолитом. Трафик постепенно перенаправляется (например, через API Gateway) с монолита на новые сервисы, пока монолит не "усохнет" и не будет отключен.

*   **Преимущества:**
    *   **Минимизация Рисков:** Монолит остается работающим во время миграции. Сбои в новом сервисе затрагивают только часть функционала.
    *   **Постепенное Освоение:** Команда постепенно осваивает разработку и управление микросервисами.
    *   **Быстрая Доставка Новых Функций:** Новый функционал (AI) может быть сразу разработан как микросервис.
*   **Недостатки:** В течение переходного периода архитектура более сложна (монолит + микросервисы).

### 6. Этапы Миграции: Планирование Трансформации Системы

Миграция разбита на этапы, основанные на логических модулях монолита и их зависимостях. График синхронизирован с Дорожной картой.

#### 6.1. Этап Подготовки (Q4 2025)

*   **Длительность:** Октябрь - Декабрь 2025.
*   **Цель:** Создать необходимую **инфраструктуру и процессы** (Принцип 9) для поддержки микросервисов и спланировать миграцию.
*   **Ключевые Задачи:**
    1.  **Анализ Монолита:** Углубленный анализ зависимостей между модулями монолита, определение четких границ будущих микросервисов (Bounded Contexts). Документирование API модулей внутри монолита.
    2.  **Развертывание Базовой Инфраструктуры для Микросервисов:**
        *   Финализация настройки кластера Kubernetes (если еще не Production Ready).
        *   Внедрение **API Gateway** (Apollo Federation) как единой точки входа. Настройка базовой маршрутизации.
        *   Настройка **Kafka Cluster** для асинхронной связи между сервисами.
        *   Внедрение **Service Discovery** (например, Consul или Kubernetes Service Discovery) для обнаружения сервисов.
        *   Настройка централизованного **мониторинга** (Prometheus/Grafana) и **логирования** (ELK/Sentry) для микросервисной среды.
    3.  **Создание Шаблонов Микросервисов:** Разработка стандартного шаблона для быстрого создания нового микросервиса (NestJS, подключение к конфигу/логам/метрикам/Kafka).
    4.  **План Миграции Данных:** Разработка стратегии миграции данных для каждого сервиса (если он будет иметь собственную БД или схему).
    5.  **Тестирование Нагрузки (Базовое):** Проведение нагрузочного тестирования текущего монолита для фиксации базовых показателей производительности перед началом миграции.
*   **Результат Этапа:** Готовая инфраструктура, спланированные границы сервисов, шаблоны для новых сервисов, понимание объема работ по миграции данных.

#### 6.2. Этап 1: Выделение Auth и User Service (Январь 2026)

*   **Длительность:** Январь 2026 (~1 месяц).
*   **Цель:** Выделить сервисы, которые имеют относительно мало внешних зависимостей (кроме БД) и используются другими сервисами (Auth - всеми, User - многими).
*   **Почему Auth и User:** Auth критически важен, но относительно независим. User также базовый, используется многими, его выделение начнет "разматывать" зависимости.
*   **Ключевые Задачи:**
    1.  **Создание Microservice:** Использование шаблона для создания сервисов `auth-service` и `user-service`.
    2.  **Перенос Логики и Кода:** Перемещение соответствующей бизнес-логики (регистрация, логин, управление профилем) и кода (Gmail API) из монолита в новые сервисы.
    3.  **Миграция Данных (при необходимости):** Если Auth/User будут иметь свою отдельную схему/БД (на старте могут использовать ту же БД Neon, но свою схему), миграция данных пользователей.
    4.  **Настройка GraphQL Schemas:** Определение GraphQL схемы для каждого нового сервиса.
    5.  **Интеграция через API Gateway:** Настройка Apollo Federation, чтобы API Gateway "знал" о новых сервисах и направлял запросы (Queries/Mutations, относящиеся к аутентификации и пользователям) на них. Клиенты продолжают обращаться к API Gateway.
    6.  **Обновление Монолита:** В монолите логика Auth/User заменяется на вызовы соответствующих микросервисов (через HTTP/GraphQL клиенты или через Gateway).
    7.  **Тестирование:** Комплексное тестирование новых сервисов изолированно и в интеграции через API Gateway. Тестирование основных пользовательских сценариев (регистрация, логин, обновление профиля). Нагрузочное тестирование выделенных сервисов.
    8.  **Деплой:** Независимый деплой новых сервисов в Kubernetes. Плавное перенаправление трафика на Gateway.
*   **Результат Этапа:** Сервисы `auth-service` и `user-service` работают независимо. Монолит использует их API.

#### 6.3. Этап 2: Выделение Chat и Notification Service (Февраль 2026)

*   **Длительность:** Февраль 2026 (~1 месяц).
*   **Цель:** Выделить наиболее нагруженный модуль (Chat) и модуль с внешними зависимостями (Notification).
*   **Почему Chat и Notification:** Чат — ядро приложения, работает с большими объемами данных и WebSocket. Notification — критически важен, зависит от Firebase и, возможно, Kafka. Их выделение значительно разгрузит монолит.
*   **Ключевые Задачи:**
    1.  **Создание Microservice:** Создание `chat-service` и `notification-service`.
    2.  **Перенос Логики:** Перемещение логики чатов, сообщений, WebSocket Gateway в `chat-service`. Перемещение логики отправки уведомлений (Firebase Admin SDK) в `notification-service`.
    3.  **Миграция Данных:** Миграция данных чатов и сообщений (возможно, с шардированием).
    4.  **Интеграция через API Gateway / Kafka:**
        *   GraphQL запросы к чатам и сообщениям направляются в `chat-service` через Gateway.
        *   **Асинхронная связь:** `chat-service` отправляет события о новых сообщениях в Kafka топик (`message.sent`). `notification-service` подписывается на этот топик и отправляет push-уведомления. Другие сервисы могут подписываться на события чата.
    5.  **Обновление Монолита:** Логика чата и уведомлений заменяется на вызовы новых сервисов или отправку сообщений в Kafka.
    6.  **Тестирование:** Тестирование производительности и надежности `chat-service` (WebSocket-соединения, скорость доставки сообщений), интеграции с Kafka и Firebase.
*   **Результат Этапа:** Чаты и уведомления работают как независимые сервисы, связанные через Kafka.

#### 6.4. Этап 3: Выделение Call и Payment Service (Март 2026)

*   **Длительность:** Март 2026 (~1 месяц).
*   **Цель:** Выделить сервисы со специфической нагрузкой (Call - WebRTC) и критически важные с точки зрения безопасности/финансов (Payment).
*   **Почему Call и Payment:** Call требует специфических протоколов и может быть ресурсоемким. Payment работает с финансовыми транзакциями и требует изоляции.
*   **Ключевые Задачи:**
    1.  **Создание Microservice:** Создание `call-service` и `payment-service`.
    2.  **Перенос Логики:** Перемещение логики WebRTC, управления сессиями звонков в `call-service`. Перемещение логики интеграции со Stripe и управления подписками в `payment-service`.
    3.  **Миграция Данных:** Миграция данных платежей (если они в той же БД, что и пользователи).
    4.  **Интеграция:** Связь через API Gateway и, возможно, Kafka (например, событие `payment.succeeded` -> Notification/User Service).
    5.  **Тестирование:** Тестирование производительности `call-service` под нагрузкой (количество одновременных звонков, качество связи). Тестирование `payment-service` и интеграции со Stripe.
*   **Результат Этапа:** Основные функциональные блоки выделены в независимые сервисы.

#### 6.5. Этап Завершения и Финализации (Апрель 2026)

*   **Длительность:** Апрель 2026 (~1 месяц).
*   **Цель:** Полностью перенести оставшуюся логику, внедрить новые функции (AI) как сервисы и отключить монолит.
*   **Ключевые Задачи:**
    1.  **Создание AI Service:** Разработка `ai-service` (может быть уже начата в Q2 2026, но финализируется сейчас). Интеграция с моделями (Claude, GPT, Gemini) и Kafka.
    2.  **Перенос Оставшейся Логики:** Перемещение любых мелких остатков логики из монолита в существующие или новые сервисы.
    3.  **Отключение Монолита:** Удаление кода монолита. API Gateway становится единственной точкой входа.
    4.  **Оптимизация и Настройка Масштабирования:** Тонкая настройка автомасштабирования (HPA) для каждого сервиса на основе реальной нагрузки. Оптимизация взаимодействия между сервисами.
    5.  **Документирование:** Актуализация всей технической документации в соответствии с микросервисной архитектурой.
*   **Результат Этапа:** Полный переход на микросервисную архитектуру. Монолит отключен. Система готова к дальнейшему независимому развитию и масштабированию сервисов.

### 7. Техническая Реализация: Построение Новой Системы Связей

#### 7.1. API Gateway (Apollo Federation)

*   **Роль:** Единая точка входа для клиентов. Агрегирует схемы GraphQL от всех микросервисов (`Auth Service`, `User Service` и т.д.) в единую схему для клиента. Может выполнять аутентификацию и Rate Limiting на входе.
*   **Технология:** Apollo Gateway.
*   **GraphQL Federation:** Микросервисы реализуют свои части схемы GraphQL, используя директивы Federation (`@key`, `@extends`, `@requires`, `@provides`). Gateway собирает эти схемы и маршрутизирует запросы к нужным сервисам.
    ```graphql
    # Пример схемы в Auth Service
    type User @key(fields: "id") { # User - корневой тип, идентифицируется по id
      id: ID!
      email: String!
      # ... другие поля Auth
    }
    type Query {
      login(input: LoginInput!): AuthPayload!
      # ... другие Auth запросы
    }

    # Пример схемы в Chat Service, расширяющей тип User
    extend type User @key(fields: "id") { # Расширяем тип User, определенный в Auth Service
      id: ID! @external # id получаем из Auth Service
      chats: [Chat!]! # Добавляем поле chats к типу User
    }
    type Chat @key(fields: "id") {
       id: ID!
       name: String
       users: [User!] # Ссылка на User
       # ...
    }
    type Query @extends {
       getChats: [Chat!]! # Расширяем корневой Query
       # ...
    }
    ```
*   **Конфигурация Gateway:** Указывает URL всех подключенных микросервисов GraphQL.

#### 7.2. Взаимодействие Между Сервисами: Синхронная и Асинхронная Связь

*   **Синхронная Связь (GraphQL через Gateway):** Сервисы могут запрашивать данные друг у друга через GraphQL API, используя API Gateway или напрямую (для внутренних запросов, если оправдано). Apollo Federation облегчает это, позволяя сервисам запрашивать поля, определенные в других сервисах.
*   **Асинхронная Связь (Kafka):** Для событий, которые не требуют немедленного ответа, используется Kafka. Это снижает связанность и повышает отказоустойчивость.
    *   **Пример:** `Chat Service` отправляет событие `message.sent` в топик Kafka. `Notification Service` подписан на этот топик и отправляет push-уведомление. `AI Service` также может быть подписан на этот топик для обработки сообщений.
    *   **Библиотека:** `kafkajs` в NestJS.
    *   **Паттерн:** Publish-Subscribe.

#### 7.3. Управление Данными

*   **Базы Данных:** Сервисы могут иметь свои собственные базы данных (разные инстансы Neon или разные схемы в одном инстансе) или совместно использовать общую базу данных, но работать только со своими таблицами. На старте возможно совместное использование БД Neon с раздельными схемами. Долгосрочно возможно шардирование БД по сервисам или по данным (например, шардирование сообщений чата).
*   **Миграция Данных:** Требуется разработка скриптов или сервисов для миграции данных из монолитной схемы в новые схемы микросервисов на каждом этапе.

#### 7.4. Инфраструктура (Kubernetes)

*   Каждый микросервис деплоится как отдельный Deployment в Kubernetes.
*   Kubernetes Services используются для внутреннего обнаружения и взаимодействия между сервисами (API Gateway -> Service).
*   Horizontal Pod Autoscaler (HPA) настраивается для каждого сервиса индивидуально.
*   Centralлизованные компоненты (API Gateway, Kafka, Redis, Prometheus, ELK) также развертываются в кластере.
*   Service Discovery (Consul или K8s built-in) помогает сервисам находить друг друга.

#### 7.5. Мониторинг и Логирование

*   Каждый микросервис экспортирует свои метрики в Prometheus и отправляет структурированные логи в централизованную систему логирования (ELK/Sentry). См. DocMonLog.md.
*   Sentry Performance Monitoring и распределенная трассировка (Distributed Tracing) становятся критически важными для отладки запросов, проходящих через несколько сервисов.

### 9. Тестирование: Проверка Надежности Новой Системы

Тестирование на каждом этапе миграции критически важно.

*   **Тесты Монолита:** Поддерживать и прогонять существующие тесты монолита до его полного отключения.
*   **Тесты Сервисов:** Каждый новый микросервис должен иметь полный набор модульных и интеграционных тестов.
*   **Тесты Интеграции:** Тестирование взаимодействия между новыми сервисами (через API Gateway, через Kafka).
*   **Тесты Миграции Данных:** Автоматизированные тесты для проверки корректности переноса данных.
*   **Нагрузочное Тестирование:** Проведение нагрузочного тестирования **всей системы** после каждого этапа миграции, чтобы убедиться, что производительность не ухудшилась и масштабирование работает. Тестирование отдельных сервисов под высокой нагрузкой.
*   **Тестирование Отказоустойчивости (Chaos Engineering, опционально):** Внедрение контролируемых сбоев (например, отключение сервиса, задержка сети) для проверки реакции системы.
